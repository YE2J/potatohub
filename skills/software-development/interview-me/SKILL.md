# Interview Me（需求采访）

## 概述

用户要的和用户真正想要的往往不同。他们要"看板"是因为习惯这么要，不是因为看板能解决他们的问题。他们说"再快点"但没给目标数字。

**找到这个差距最便宜的时刻是在任何方案、规格、代码存在之前**。一旦开始构建，切换成本是真实的，用户会把错的东西合理化成"够好了"——错配就被锁死。

这个 skill 在它花钱之前关上差距。其他 Define 阶段 skill 假设你大致知道要什么：`idea-refine` 从想法生成变体，`spec-driven-development` 把需求写下来，`doubt-driven-development` 在草拟后压力测试方案。Interview-me 是所有这些之前的部分：**一次问一个问题，附上你的最佳猜测**，直到你能在用户开口前预测他要说什么。

## 何时使用

- 需求缺至少一项：**谁**在用、**为什么**要、**成功**长什么样、绑定**约束**是什么
- 需求是惯例式而非具体的（"给我建个 X"、"弄快点"），不猜就无法拆解惯例
- 你忍不住想从没摆出来的假设开始
- 两个合理的价值在张力中（简单 vs 灵活、成本 vs 速度），用户没说优化哪个
- 用户显式召唤："interview me"、"grill me"、"开始前我们确定吗？"、"压力测试我的想法"

**何时不用**：需求无歧义且自足（"重命名这个变量"）、用户明确要速度、纯信息请求（"X 怎么工作？"）、机械操作、你已有 ≥95% 信心（先重读停止条件）。

## 加载约束

这个 skill 需要**在线响应的用户**。不要在非交互上下文（cron 定时任务、自主运行）调用。那种场景需求含糊时，把它作为 blocker 摆给用户，不要猜。

## 流程

### Step 1: 假设 + 信心数字

问任何问题之前，写下你对用户想要什么的最佳解读（一句话）+ 诚实的信心数字（0–100%）：

```
HYPOTHESIS: 你想要一种在站会上回答"我们进展如何"的方式，"看板"是跳出来的惯例说法。
CONFIDENCE: ~30% —— 缺：给谁用、"指标"在语境里指什么、成功什么样
```

数字强迫诚实。如果你写了个高数字却预测不了用户对你接下来三个问题的反应，数字是错的。从你能辩护的信心水平开始。

信心低于 ~70% 时，同行附上一行理由——还缺什么/什么未解决。这让用户知道采访需要浮现什么。

### Step 2: 一次一问，每问带猜测

格式：

```
Q: <一个聚焦的问题>
GUESS: <你对答案的假设 + 产生它的推理>
```

等用户反应后再问下一个。

**为什么一次一问而非批量：**
- 把假设埋进列表，用户没法逐个反应
- 批量鼓励扫读和表面答案
- 第三个问题往往依赖第一个问题的答案；一起问会锁死错误框架
- 用户认真思考的精力有限，一次花一个问题

**为什么带猜测：**
- 用户对错误猜测的反应快于从零生成答案
- 把你承诺给一个可以被证明错的假设上，保持诚实
- 暴露*你的*假设——这正是采访要暴露的

风险：礼貌的用户为了附和而同意你的猜测。缓解：明显表现出愿意犯错，偶尔朝你预期用户会反驳的方向猜。

### Step 3: 听"想要 vs 应该想要"

最危险的回答是用户说出听起来很深思熟虑的话，而非他们真正想要的。注意：

- 模式匹配最佳实践话术（"我要它可扩展"、"干净架构"）而没有具体内容
- 从众式回答（"大多数 app 都这样"、"标准做法"）
- "我大概应该……"、"我觉得我该……"、"好的工程实践说……"
- 流行词当目标——"现代"、"可扩展"、"健壮"是答案而非具体结果

听到这些时，该问的问题是：

> "如果你不需要向任何人证明这个决定，你实际想要的是什么？"

这一个问题往往比前五个问题干更多活。

### Step 4: 用用户自己的话复述意图

信心高时，写回你认为用户想要的。紧凑（5–8 行），尽量用他们的语言，结构化到用户能逐行确认或纠正：

```
这是我现在认为你想要的：

- Outcome:      <一行>
- User:         <一行——谁受益>
- Why now:      <一行——什么变了>
- Success:      <一行——怎么知道成了>
- Constraint:   <一行——绑定限制>
- Out of scope: <一行——明确不做什么>

是 / 否 / 补充？
```

**"Out of scope" 不可省略**。一半的错配是双方对*不*做什么的静默分歧。

### Step 5: 确认——显式"是"，不是"随你"

关卡是显式"是"。以下**不是**：

- "随你定最好。" → 用户在授权，意味着他也没 95% 信心。用两个具体选项重问。
- "听起来不错。" → 含糊。问："有要补充的吗？" 沉默不是确认。
- "行，开始吧。" → 常是礼貌性退出，不是背书。同样追问。
- 沉默后"好了开始" → 用户放弃了采访而非收敛。停下问是否漏了什么。

用户纠正就折进来重新复述。循环直到显式"是"。

### 95% 信心停止

当你对下面这个能答"是"就完成：

> *我能预测用户对我接下来三个问题的反应吗？*

能 → 有共识了。停止采访，产出复述。不能 → 没完成，问下一个问题。

这是可检查的测试，不是感觉。也有下限：问了几轮仍预测不了 → 这是关于需求的信息，不是继续磨的理由。停下告诉用户："我问了 X 个问题仍无法预测你的反应。有根本性的东西缺失。要退一步吗？"

## 输出

这个 skill 的产出是**确认过的意图声明**：Step 4 的复述 + Step 5 的显式"是"。方案、计划、任务清单是下游——它们消费这个 skill 产出的意图。

用户想让意图持久（多会话项目、移交给协作者）→ 提议保存为 `docs/intent/[topic].md`。只在用户确认后保存。

## 示例

**没有 interview-me：**
```
用户:  给我建个指标看板
Agent: <开始提图表库和布局>
```
Agent 已假设：给谁用、什么指标、"我们团队"什么意思、成功什么样。全都没说。每个假设都是用户以后能说"我不是这个意思"的地方。

**有 interview-me：**
```
用户: 给我建个指标看板

Agent:
HYPOTHESIS: 你想要一种在站会上回答"我们进展如何"的方式，"看板"是跳出来的惯例。
CONFIDENCE: ~30% —— 缺：给谁用、指标是什么、成功什么样

Q:     你说"进展如何"时是谁在问——你自己、工程团队站会、还是向上汇报（经理/高管）？
GUESS: 工程团队站会，因为"我们"通常这么界定，而且这个问题在站会里被问。如果是给高管的，指标和框架会差很多。

用户: 其实是我自己。我总搞不清哪些策略在跑、早期信号什么样。

Agent:
更新解读：不是团队看板，是个人策略追踪器。信心 ~60% —— 还缺："早期信号"指什么、完成什么样。

Q:     缺口是你不知道有哪些策略在跑，还是没法在一个地方看它们的结果？
GUESS: 第二个。你某处有策略列表，但结果散在五个工具里，手动对账才是你烦的。

用户: 其实是第一个。我根本没有列表，它们散在各文档里。

Agent: <继续>
```

两个问题后，Agent 发现实际需求不是"看板"，而是"清单"。不同工件、不同范围、不同工作量。看板会是错的。

## 与其他 Skill 的交互

- **`doubt-driven-development`**：时间线两端。Interview-me 是决策前意图提取；质疑驱动是决策后工件审查。都抓分歧，但在不同时刻。
- **`source-driven-development`**：正交。Interview-me 澄清用户要什么；SDD 验证框架事实。
- **`plan` / spec 流程**：下游。确认的意图足够具体后，交给方案设计写下来。

## 常见合理化借口（防自欺表）

| 借口 | 现实 |
|:---|:---|
| "需求够清楚了" | 如果你现在写不出用户想要的结果的一句话，需求就不清楚。先跑 Step 1。 |
| "问太多问题浪费他们时间" | 4–6 个针对性问题浪费的时间很少。建错东西浪费的时间巨大，而且是用户承担。 |
| "边建边想" | 代码存在后的切换成本是现在的 10 倍。实现中的发现就是返工。 |
| "他说'随你定'，我应该自己决定" | "随你定"是授权，不是决策。用两个具体选项重问。 |
| "我应该给他几个选项选" | 选项在用户知道自己要什么、在两个权衡间选时有效。他不知道。列选项加宽搜索；提问收窄它。 |
| "带猜测会引导他" | 引导正是目的。反应比从零生成快。风险是谄媚而非引导；用明显愿意犯错来缓解。 |
| "聊够了，我懂了" | 测试：能预测他接下来三个问题的反应吗？不能就还没懂。 |
| "用户说是了，完成了" | 如果"是"跟着含糊复述或开放式"听起来不错"，"是"是空的。具体复述再确认。 |

## 红旗（Red Flags）

- 一条消息三个以上问题：那是批处理，不是采访
- 不带假设的问题：那是调查，不是承诺
- 把"随你定最好"当终态接受
- 用户显式确认复述之前产出方案/计划/任务清单
- 问"什么是最佳实践？"而非"你实际想要什么？"
- 用户给"可扩展/干净/现代"这类信号回答就接受，不深挖是否真是他要的
- 三轮以上信心没明显上升：你在问错问题，退一步重新框
- 低于 ~70% 的信心不带理由：用户不知道缺什么就无法帮你补
- 用户确认前保存意图文档（文档本身暗示了用户没给的"是"）
- 复述省略 "Out of scope" 行（对非目标的静默分歧占错配的一半）

## 验证清单

- [ ] 第一轮就陈述了带信心数字的显式假设
- [ ] 每个低于 ~70% 的信心数字带一行理由（还缺什么/未解决什么）
- [ ] 一次问一个问题，每个带猜测
- [ ] 用户给出信号/惯例式回答时，至少跑了一次"不向任何人证明的话你实际想要什么？"探针
- [ ] 写了具体复述（Outcome / User / Why now / Success / Constraint / Out of scope）给用户
- [ ] 用户用显式"是"确认（不是"随你定"、"听起来不错"、沉默）
- [ ] 停止时能预测接下来三个问题的反应
- [ ] 移交下游（spec/plan）时用确认过的意图表述，不是原始含糊需求
