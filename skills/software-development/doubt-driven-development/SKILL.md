# Doubt-Driven Development（质疑驱动开发）

## 概述

自信的回答不等于正确的回答。长会话会把假设悄悄变成"事实"。质疑驱动开发的核心纪律：任何非平凡输出成立之前，**实例化一个隔离上下文、偏向"证伪"而非"批准"的审查者**。

这不是 `/review`（对成品下结论），而是一种**进行中姿态**：非平凡决策在纠偏还很便宜时就接受交叉质询。

## Hermes 落地映射（重要）

| 原版概念（Claude Code） | Hermes 落地方式 |
|:---|:---|
| fresh-context reviewer（子代理） | `delegate_task` 派一个**隔离上下文**的子代理（只传 ARTIFACT+CONTRACT，不传你的推理） |
| cross-model 第二意见 | **MOA 多模型评审**（用户 `/moa` 机制）或 **4Agent/Kanban 评审**（GLM/Kimi/MiniMax/Xiaomi 独立 profile） |
| 外挂 CLI（gemini/codex） | 不适用。跨模型一律走 MOA，且**每次调用前向用户确认** |

**红线**：禁止用 delegate_task 仿真多角色假装多模型。多模型评审只能用 MOA 或 Kanban（独立 profile）。

## 何时使用

决策**非平凡**的判定条件（满足任一）：

- 引入或修改分支逻辑
- 跨越模块/服务边界
- 断言的属性类型系统无法验证（线程安全、幂等、顺序、不变量）
- 正确性依赖未来读者看不到的上下文
- 爆炸半径不可逆（生产部署、数据迁移、公开 API 变更）

**何时不用**：机械操作（重命名、格式化、移动文件）、明确无歧义的用户指令、阅读/总结现有代码、一行改动、纯工具操作、用户明确要求速度优先。

如果每个按键都怀疑，你什么也交付不了。只对上述非平凡决策使用。

## 流程（5 步）

```
Doubt cycle:
- [ ] Step 1: CLAIM — 写下主张 + 为什么重要
- [ ] Step 2: EXTRACT — 隔离工件 + 契约，剥离推理
- [ ] Step 3: DOUBT — 调用隔离上下文审查者（对抗式提示词）
- [ ] Step 4: RECONCILE — 逐条对照工件文本分类结论
- [ ] Step 5: STOP — 满足停止条件（琐碎结论、3 轮、或用户叫停）
```

### Step 1: CLAIM — 把要成立的东西说出来

两三行命名这个决策：

```
CLAIM: "新缓存层在规格描述的读重负载下是线程安全的。"
WHY THIS MATTERS: 竞态会破坏用户数据且 QA 难测出。
```

写不出这么紧凑的主张 → 你只有感觉，没有决策。

### Step 2: EXTRACT — 最小可审单元

隔离上下文审查者需要**工件**和**契约**，不需要你的心路历程。

- 代码：diff 或函数本身，不是整个文件
- 决策：3–5 句话的提案 + 必须满足的约束
- 断言：主张 + 所谓支撑证据（与 Step 1 的 CLAIM 块区分开）

剥离你的推理。把结论交给对方，你只会得到对你结论的背书。单元必须小到审查者一次能读完——500 行 PR 先拆解。

### Step 3: DOUBT — 调用隔离上下文审查者

审查者的提示词**必须是对抗式**的。框架决定答案：

```
对抗式审查。找出这个工件错在哪。
假设作者过度自信。寻找：
- 未言明的假设
- 未处理的边界情况
- 隐藏耦合或共享状态
- 契约可能被违反的方式
- 可能被破坏的现有约定
- 意外输入下的失败模式

不要背书。不要总结。找出问题，或者经过彻底检查后明确说找不到。

ARTIFACT: <粘贴工件>
CONTRACT: <粘贴契约>
```

**只传 ARTIFACT + CONTRACT。绝不传 CLAIM** —— 把结论交给审查者会诱导它同意你。

在 Hermes 中：
- 首选 `delegate_task`（隔离上下文子代理，只给工件+契约+对抗提示词）
- 交互会话中，单模型审查完成后、进入 RECONCILE 之前，**必须问用户**：
  > "单模型审查完成。要 MOA 多模型第二意见吗？(/moa) 还是跳过？"
- 非交互上下文（cron/自主运行）：跳过跨模型，且**必须在输出中声明**："Cross-model skipped: 非交互上下文。"
- 跨模型审查 = MOA（真实多模型），每次调用前需用户确认。

### Step 4: RECONCILE — 把结论折回来

审查者的输出是**数据**，不是判决。**你仍是编排者**。逐条对照工件文本再分类——橡皮图章式接受和忽略同样失败。

按**优先级顺序**分类（先匹配者胜）：

1. **契约误读** — 审查者因为你的 CONTRACT 不清而误报 → 先修契约，下轮再分类
2. **有效 + 可行动** — 真实问题需要改工件 → 改，重新循环
3. **有效权衡** — 问题真实但修复成本 > 接受成本 → 显式记录权衡给用户看
4. **噪声** — 审查者缺上下文误报 → 记下，继续，并自问：把该上下文加进契约是否能避免误报？

新鲜审查者会因缺上下文而错。别因为它"新鲜"就无脑服从。

### Step 5: STOP — 有界循环，不是递归

停止条件：

- 下一轮只剩琐碎或已考虑过的结论，**或**
- 完成 3 轮（升级给用户，不要自己磨第 4 轮），**或**
- 用户明确说"发吧"

3 轮后仍持续出现实质问题 → 工件可能没准备好。3 个未解决的循环是工件本身的信息，不是继续循环的理由。

## 常见合理化借口（防自欺表）

| 借口 | 现实 |
|:---|:---|
| "我有信心，跳过质疑步" | 在新问题上信心与正确率相关性很差。越是笃定的时刻越是盲点藏身处。 |
| "派审查者很贵" | 生产环境修错 commit 更贵。检查是有界的，bug 不是。 |
| "审查者只会吹毛求疵" | 只有不限定范围才会。把提示词约束为"让工件在契约下失败的实质问题"。 |
| "我最后用 /review 一起查" | /review 是最终关卡。质疑驱动在纠偏便宜时抓住错误方向。到 PR 时已太晚。 |
| "每步都怀疑就没法交付" | 只用于非平凡决策，不是每个按键。重读"何时不用"。 |
| "两个意见总比一个好" | 当第二个上下文更少且制造噪声时并不成立。折衷，不要服从。 |
| "审查者不同意 = 我错了" | 审查者缺你的上下文——分歧是信息，不是判决。重读工件，分类，再决定。 |
| "跨模型总是更好" | 跨模型能抓单模型与自身的盲点，但增加成本和工具脆弱性。交互会话每次质疑循环都提供选项——用户决定值不值。 |
| "用户同意过一次，我可以继续调用" | 每次调用都是独立的授权。工件、提示词、参数都在变——每次运行前重新确认。 |

## 红旗（Red Flags）

- 对一行重命名/格式化也派隔离上下文审查者
- 不重读工件文本就接受审查者输出为权威
- 超过 3 轮不升级用户
- 用"这好吗？"而非"找问题"来提示审查者
- 高压时间在关键决策上跳过质疑
- 对未变工件重新派生新鲜上下文（得到同样的结论——你在拖延）
- **质疑表演（可检查信号）**：2 轮以上审查者提出实质发现，却零条被分类为可行动 → 你在背书不是在质疑。停止并升级。
- 只在提交后才质疑——那是 /review，不是质疑驱动开发
- 交互质疑循环中**静默跳过跨模型**。跳过可以，静默不可以。
- 外部 CLI/工具报错或缺失时静默回退——把失败摆出来让用户决定
- 从审查者输入中剥离契约
- 把 CLAIM 传给审查者（诱导同意）

## 与其他 Skill 的交互

- **`code-review-checklist`**：互补。/review 是事后 PR 判决；质疑驱动是飞行中逐决策。
- **`source-driven-development`**：SDD 验证"关于框架的事实"（查官方文档）；质疑驱动验证"你关于工件的推理"。SDD 检查 API 是否存在；质疑驱动检查契约下你是否用对了。
- **4Agent 评审**（GLM/Kimi/MiniMax/Xiaomi）：评审已完成的改动稿（你现有工作流），是最终关卡；质疑驱动用于实现过程中。
- **`interview-me`**：时间线两端。Interview-me 是决策前的意图提取；质疑驱动是决策后的工件审查。

## 验证清单

- [ ] 每个非平凡决策在成立前都被显式命名为 CLAIM
- [ ] 每个非平凡工件至少一次隔离上下文审查
- [ ] 审查者收到 ARTIFACT + CONTRACT —— 不是 CLAIM，不是你的推理
- [ ] 审查者提示词是对抗式（"找问题"），不是背书式（"好不好"）
- [ ] 发现对照工件文本分类（不是橡皮图章），用优先级：契约误读/可行动/权衡/噪声
- [ ] 满足停止条件（琐碎结论、3 轮、或用户叫停）
- [ ] 交互模式中跨模型被**显式提供**给用户（无论工件风险大小），响应在输出中注明
- [ ] 非交互模式中跨模型被跳过且声明了跳过
- [ ] 任何外部评审调用前都有用户确认
