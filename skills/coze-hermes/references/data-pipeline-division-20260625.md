# 数据管线分工决议 (2026-06-25)

## 背景

Coze 与 Hermes 讨论 A 股数据管线的职责划分。原方案为 Coze 拉不复权行情（恒生聚源）+ Hermes 拉复权因子（Tushare）并本地做前复权计算。三方 Agent 并行评审后，因 Tushare 积分0 无法调用 adj_factor 接口，推翻原方案。

## 最终方案

**Coze 统一提供所有行情数据，Hermes 纯消费。**

| 数据 | 来源 | 目标表 |
|------|------|--------|
| 不复权原始行情 | Coze 恒生聚源 MCP → dz_dailyquote | `stock_data.db::dz_dailyquote` |
| 前复权日K线 | Coze 腾讯 fqkline API → 直接返回 | `stock_data.db::daily_kline` |

### 放弃的方案

- **Tushare adj_factor 本地计算**：积分=0，接口返回 `频率超限(1次/小时)`，不可用。即使充值也需 28 分钟串行拉取 5,527 只。
- **多数据源混合**：恒生聚源/Tushare/腾讯三方复权算法可能不同，混用引入 0.1%~1% 口径偏差。

## 待确认问题（2026-06-25，等待 Coze 回复）

1. **推送方式**：CSV 下载链接 / 共享目录轮询 / 其他？
2. **增量范围**：全量 5,527 只还是 99 只自选股？
3. **历史数据导入**：`qfq_klines.csv`（256 万行）一次性导入 `daily_kline` 表？

## 三方 Agent 评审摘要

| Agent | 维度 | 核心发现 |
|-------|------|---------|
| ① 数据工程 | 可行性 | Tushare MCP adj_factor 限频 1次/小时，全量拉取需要 230 天，不可行 |
| ② 架构 | 合理性 | 职责分离合理，但 fillna(1.0) 静默降级和 90 天清理策略有隐患 |
| ③ 风险&替代 | 成本 | 方案 C（腾讯 fqkline）免费无限频，推荐为最终方案 |
