# MOA 聚合器教训（2026-08-05 会话实测）

## 1. 静态结论必须运行时验证

**场景**：用户报「输入 /moa 显示没有匹配项」。初查只 grep 了桌面端静态命令列表（`apps/desktop/src/lib/desktop-slash-commands.ts`），发现无 moa 条目就下结论"桌面端未注册 /moa，不可用，需改源码"。

**实际真相**（用户重启后验证）：
- `/moa` **后端一直存在**（`hermes_cli/commands.py:162` 注册表）
- 桌面端有 **extension command 兜底**（`desktop-slash-commands.ts` 的 `isDesktopSlashExtensionCommand`：不在静态列表的未知命令仍允许执行）
- "没有匹配项"是**输入框自动补全列表**没有它，回车后命令走 extension 路径正常执行
- 重启后"好了" = 前端命令补全索引/缓存刷新，重新发现了后端命令

**教训**：静态列表缺失 ≠ 功能不可用。查命令可用性必须查**运行时执行路径**（extension fallback、后端注册表），不能只看前端静态清单。这呼应记忆里"代码审查必须执行环境验证"的 5 维度。

## 2. 聚合器不盲从也不盲拒参考模型

**场景**：MOA 评审 orchestrator 优化方向时，聚合者（本会话）的 SQL 查询把 `started_at`（Unix **秒**）当毫秒处理，得出"1970-01-22 / 近30天0会话"假象。参考模型 deepseek 指出时间戳单位错误。

**正确处理**（本会话实际做的）：
- 接受参考模型的质疑 → 用正确列名/单位重查 → 得到"2026-06-16 → 08-05，今日活跃"的**修正后证据**
- 结论建立在修正后的数据上，不基于最初的假象

**教训**：参考模型提出的"验证要求"是质量审查信号，不是字面执行指令，也不是可忽略噪声。聚合时要逐条核实，用真实执行结果仲裁，而不是在假数据上继续推理。

## 3. 决策证据链要可回溯

- 四方向评估给出明确票型（5/5、0/5）而非模糊"多数认为"
- 数据验证（会话数、时间跨度、Kanban 表位置）逐项列证据来源
- 聚合报告标注"过程教训"：初始查询 bug → 修正 → 最终结论，让用户看到数据可信度
