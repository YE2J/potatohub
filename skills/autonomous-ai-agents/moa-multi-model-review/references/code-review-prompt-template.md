# MOA 代码评审 Prompt 模板

## 结构

一个有效的 MOA 代码审查请求包含 4 层：

```
1. **文件清单** — 路径 + 行数 + 核心职责
2. **上下文** — 这次改了什么（diff 摘要，不是 git diff 全文）
3. **评估维度** — 4 个固定维度：代码质量 / 逻辑正确性 / 边界条件 / 安全风险
4. **特定检查点** — 当前代码特有的易错处（日期格式、SQL注入、依赖顺序等）
```

## 完整模板

```
请评审以下文件，从代码质量、逻辑正确性、边缘情况和SQL注入风险四个维度交叉验证。
请输出发现的每个问题及其严重等级(P0/P1/P2)和修复建议。

**文件1**: `<path>`（<行数>行）
核心职责/本次改动：
- 改动点1
- 改动点2

**文件2**: `<path>`（<行数>行）
...

**评估重点**：
1. <特定易错点1，如日期格式兼容性>
2. <特定易错点2，如作用域问题>
3. <特定易错点3，如未调用的函数>
4. <特定易错点N>

请逐条给出结论，每条说明风险等级和修复建议。
```

## 实际案例

本目录的 `moa-multi-model-review/` skill 就是由一轮 MOA 审查驱动的。完整 prompt 如下：

```
请评审以下两个文件，从代码质量、逻辑正确性、边缘情况和SQL注入风险四个维度交叉验证...

评估重点：
1. report_weekly_top_sectors() 中累计计算的逻辑是否正确
2. 日期格式在两张表之间是否兼容（YYYY-MM-DD vs YYYYMMDD）
3. 简化模式下的查询是否使用了正确的日期
4. is_data_unchanged() 正则匹配是否可靠
5. truncate优先级设置是否合理
6. SQL注入风险：f-string拼接表名
...
```

## 风险等级定义

| 等级 | 含义 | 处理 |
|:----:|------|------|
| **P0** | 运行时崩溃或数据错误 | 必须修，否则功能异常 |
| **P1** | 逻辑不严谨或代码效率低 | 建议修，否则长期隐患 |
| **P2** | 可读性/健壮性改进 | 有余力时修 |

## 经验

- **命名作用域**（P0 高频来源）：变量在 try 块内定义却在外部引用，try 异常跳过后 NameError
- **日期格式不兼容**（P0 高频来源）：不同表的 trade_date 列可能是 YYYYMMDD 或 YYYY-MM-DD
- **定义未调用**（P1 常见）：旧版本遗留的函数在新版本没被调用
- **硬编码阈值**（P1 常见）：写死的数字在动态数据量下不适用
- 聚合模型会自动收敛矛盾点——如果两个模型指出同一个问题，一定是真问题
