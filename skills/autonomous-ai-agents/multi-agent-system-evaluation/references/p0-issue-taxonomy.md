# P0 Issue Taxonomy (来自 2026-07-09 四模型评审)

四模型Kanban评审（GLM/Kimi/MiniMax/DeepSeek）在对P1数据设施做第二轮评审时发现的**7类P0问题**。
可作为未来评审的检查清单，确保评审覆盖全面。

## 7大P0类别

### 1. 🔴 数据格式不统一
**信号**: 同一个概念（股票代码、日期）在不同表中用不同格式存储。
**典型发现**: `daily_kline.stock_code=000001`（纯数字）vs `ths_member.con_code=000001.SZ`（带后缀）。
**修复**: 不做全量数据迁移（6.5GB风险高），建查询层标准化函数。

### 2. 🔴 配置/PRAGMA仅局部生效
**信号**: 设置了优化参数但实际连接读不到。
**典型发现**: SQLite PRAGMA (cache_size/mmap) 只在 `get_conn()` 中设置，但50+处`sqlite3.connect()`绕过。
**修复**: 统一连接管理函数，批量迁移脚本。

### 3. 🔴 事务安全问题
**信号**: 先删后写没有BEGIN/ROLLBACK事务包裹。
**典型发现**: `daily_sector_moneyflow.py` 先DELETE再INSERT，中间出错数据丢失。
**修复**: 加`BEGIN`/`COMMIT`/`ROLLBACK`，确保操作原子性。

### 4. 🔴 数据映射/匹配失败
**信号**: 行业名、板块代码等用来做JOIN或配置匹配的字段对不上。
**典型发现**: 估值配置表行业名与THS行业分类名52%不匹配（后改为用sector_code匹配100%通过）。
**修复**: 用编码(code)而非名称(name)做关联。

### 5. 🔴 数据表为空/过少
**信号**: 表存在但行数=0，或数据不完整。
**典型发现**: `adj_factors` 基本空表（0行）、`moneyflow_daily` 29行date列被stock_code污染。
**修复**: 回填或清洗。

### 6. 🔴 路径/版本硬编码
**信号**: 脚本中写死绝对路径或调用系统默认版本。
**典型发现**: `db_utils.py:32` 硬编码 `/Users/yellow/my_quant_system/stock_data.db`；`moneyflow_pipeline.sh` 用`python3`（系统3.9.6）而非3.11.11。
**修复**: 相对路径/env变量；指定Python版本。

### 7. 🔴 0字节残留文件
**信号**: 文件存在但size=0，可能是废弃占位文件。
**典型发现**: `data/*.db` 下4个0字节文件，干扰文件查找，在备份/恢复时浪费时间。
**修复**: 确认无引用后删除。

## P0判定原则

判定为P0的条件（至少满足一条）：
1. **数据丢失**: 阻塞级数据完整性受损（如事务未提交、数据被覆盖）
2. **查询错误**: 跨表JOIN必然失败（如stock_code格式不统一）
3. **性能退化**: 整体系统性能大幅下降（如PRAGMA未生效导致全表扫描）
4. **不可恢复**: 运行时错误导致数据不可逆损坏
5. **跨文件不一致**: 多个文件对同一逻辑的表述冲突（如CLI文档用`--parent`实际不能用）
