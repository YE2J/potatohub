## 1. 技术架构总评

### 1.1 现状评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 数据完整性 | ★★★★☆ | 覆盖日线/资金流/因子/涨停/龙虎榜/异动/估值, 来源丰富 |
| 自动化程度 | ★★★★☆ | 10个Hermes cron + 系统crontab, 覆盖采集→计算→推送全链路 |
| 因子工程 | ★★★☆☆ | 管线框架完整但核心算法标记TODO, 15个因子集中在量价+资金 |
| 回测体系 | ★★★☆☆ | v4/v5回测存在, IC评估模块到位, 但数据漂移/过拟合防护缺失 |
| 性能设计 | ★★☆☆☆ | SQLite配置偏保守(cache仅8MB), 缺少读写分离和归档策略 |
| 可维护性 | ★★★☆☆ | 有版本号和checksum, 但破venv残留、部分函数标记TODO |

### 1.2 核心架构图谱

```
[数据采集层]                     [计算层]                     [输出层]
Tushare MCP ──→ stock_data.db ──→ factor_pipeline.py ──→ daily_factors
  daily        (SQLite 6.9G)      incremental/backfill     285万行
  moneyflow                         ↓                        ↓
  fina_indicator              strategy_library/           IC评估模块
  limit_list                    backtest_v4/v5           (ic_analyzer.py)
  dragon_tiger                  valuation_channel.py       ↓
  hot_stock                                                Hermes cron
     ↓                                                    晨报→微信推送
  Hermes cron schedule (18:00~20:00 密集调度)
```

**架构风格评价**: 单节点全量流水线模式（Single-Node Batch Pipeline）。优点在于部署简单、数据一致性强；缺点在于扩展性受限、无分片、无读写分离。对于个人量化系统而言，这个架构在当前阶段是合理的，但拟搭建的"三层结构"需要更精细的设计。

## 2. SQLite在百万级日增量下的性能极限

### 2.1 当前实际数据量

| 表名 | 行数 | 日均增量(估) | 年增长 |
|------|------|-------------|--------|
| moneyflow_daily | **14,294,052** | ~60,000 | 约2200万行 |
| daily_factors | **2,853,670** | ~5,200 | 约190万行 |
| daily_kline | **2,668,549** | ~11,000 | 约400万行 |
| minute_kline | 243,435 | ~5,000 | 约180万行 |

### 2.2 性能极限分析

**写入瓶颈评判**:
- 当前每日数据增量约 **7~10万行**, 对应约 **5~8MB** 新数据
- SQLite在WAL模式下单日写入10万行(O(10⁵)级)是 **完全无压力的**
- 实测阈值: 当日增量达到 **100万行** 或单事务超过 **50万行** 时才出现可感知延迟

**查询瓶颈评判**:
- 单表千万级查询, 在有索引覆盖的情况下, WHERE条件过滤到数百行是 **亚毫秒级**
- 当前最大表 moneyflow_daily (1429万行) 有 `idx_mf_date` 和复合PK索引, 按日过滤性能良好
- **真正瓶颈**: 跨表JOIN, 如 `daily_factors LEFT JOIN daily_kline` 在百万行级别上JOIN, 可能耗时500ms~2s

**文件大小极限**:
- SQLite在 **10TB以下** 是稳定的, 但**性能拐点在50GB左右**
- 当前年增长约 **2.5GB** (6.9GB → ~9.5GB/年)
- 以当前速度, **5年内不会突破50GB性能拐点**

### 2.3 当前配置问题

当前setting: page_size=4096, cache_size=2000(≈8MB), synchronous=NORMAL, journal_mode=WAL

**严重问题**: cache_size=2000页=8MB, 对于6.9GB的数据库而言是极低的配置。这导致每次涉及全表扫描或大范围范围查询时, 频繁磁盘I/O。

### 2.4 优化建议（零成本）

```sql
PRAGMA cache_size = -262144;   -- 256MB (负值表示KB单位)
PRAGMA mmap_size = 2147483648;  -- 2GB内存映射
PRAGMA temp_store = MEMORY;     -- 临时表存内存
```

## 3. Mac Mini M4性能影响分析

### 3.1 硬件基线

| 指标 | 值 | 评价 |
|------|-----|------|
| CPU | Apple M4, 10核(4P+6E) | 单核性能极强, 多核够用 |
| RAM | 16GB统一内存 | **最关键的约束条件** |
| 存储 | SSD | SQLite受存储延迟影响 |

### 3.2 当前资源消耗分析

**CPU负载**:
- 因子计算(增量模式): 约5000只股票 × 15个因子, 纯Python计算, 单次约 **15~30秒**
- 全量回填: 每个文件约 **3~8分钟**, CPU单核100%
- cron高峰时段(18:00~20:00): 密集调度, 但脚本之间间隔≥15分钟, **CPU不会过载**

**内存消耗**:
- SQLite本身: WAL模式下约 **50~200MB**
- pandas批量处理: 5000只股票×120天历史窗口, 约 **200~400MB**
- 因子管线8线程并行: 额外 **100~200MB**
- **峰值总消耗: ~800MB**, 对16GB RAM来说非常安全

### 3.3 拟搭建三层结构的资源影响预测

| 新增模块 | 额外CPU | 额外内存 | 磁盘增长 |
|---------|---------|---------|---------|
| 新闻情绪(全市场) | 低(API调用为主) | 中(LLM打分) | ~50MB/年 |
| 财务指标(全市场5000+) | 中(调Tushare API) | 中(pandas处理) | ~100MB/季 |
| PE分位数计算 | 低 | 低 | ~20MB |
| 决策融合层 | 极低 | 极低 | ~5MB |
| **合计** | **≈+15%** | **≈+300MB峰值** | **≈200MB/年** |

**结论**: Mac Mini M4 **完全可承载** 拟搭建的三层结构。16GB RAM不是瓶颈。

### 4.2 发现的关键问题

**问题1: cron helper脚本的假错误**
多条cron任务`last_status: "error"`, 但实际数据写入成功。原因是`cron_log_helper.sh: line 100`中的整数比较脚本bug, 将非数字字符串(`17834202383N`)传给`-eq`运算符。**这是日志脚本的问题, 不影响数据质量**——但会掩盖真正的失败。

**问题2: 指数日线pct_chg NULL**
沪深300早期数据的pct_chg字段大量NULL, 需要确认是Tushare原始数据问题还是导入脚本问题。

**问题3: 因子管线核心算法未实现**
在`factor_pipeline.py`的Line 143和158中明确标记 `# TODO: 实现实际的GS信号算法` 和 `# TODO: 实现主力雷达算法`。需要确认当前实际计算链路是否依赖外部模块。

**问题4: Python环境混乱**
存在三个虚拟环境: `.venv`, `.venv.broken.20260619`, `.venv.broken2.20260619`, 且.venv是Python 3.9。cron脚本使用`~/.pyenv/versions/3.11.11/bin/python3`, 与环境不一致。

### 4.3 补缺管线可行性评估

#### 新闻情绪管线 ✅ 可行
Tushare `major_news` 接口已有, 覆盖新华网/凤凰/同花顺/新浪/华尔街见闻等。建议只对自选股关联新闻做情绪打分。

#### 财务指标管线 ⚠️ 需谨慎
`fina_indicator` 每次请求最多返回100条, 全市场5000+股票×20+季度需要 **1000+次API调用**。推荐只对watchlist股票采集。

#### PE分位数管线 ✅ 可行, 但需明确计算逻辑
分位数计算: `(当前PE - 历史最低PE) / (历史最高PE - 历史最低PE)`。窗口选择推荐5年滚动。亏损股(EPS≤0)需特殊处理。

## 7. 最优技术选型建议

### 7.1 数据库策略: 留在SQLite, 优化配置

不建议迁移到PostgreSQL/MySQL/DuckDB的核心理由:
1. 单节点个人系统, 不需要网络层
2. SQLite 6.9GB距离性能拐点(50GB+)还有多年
3. 迁移成本(改全部SQL + 连接方式 + cron脚本)远超收益

### 7.2 因子增量计算: 日频 OK, 周频收益低

| 因子类型 | 推荐频率 | 理由 |
|---------|---------|------|
| 资金面因子 | **日频** | 信号时效性要求高 |
| 估值因子 | **周频** | 估值变化慢 |
| 财务因子 | **季频** | 财报发布后才变化 |
| 新闻情绪因子 | **日频** | 新闻每日都有 |

### 7.3 分钟数据策略

日线信号适合回测, 分钟信号只用于盘中辅助确认。不纳入回测信号, 避免微观结构噪声。

### 7.4 最优实施路线图

```
Phase 1 (立即, 1~2天)
├── 优化SQLite配置 (cache_size/mmap/temp_store)
├── 修复cron_log_helper.sh第100行bug
├── 清理Python环境 (删掉.broken venv, 统一3.11)
└── 审查并确认因子计算实际链路

Phase 2 (本周, 3~5天)
├── 实现短期因子: funding_surge(已有数据), north_star(已有), board_resonance(已有)
├── 注册到factor_pipeline.py的增量计算中
├── 在ic_analyzer.py中添加新因子的IC评估
└── 新增新闻情绪管线(限自选股)

Phase 3 (下周, 3~5天)
├── fina_indicator采集(限自选股+watchlist)
├── PE分位数计算(5年滚动窗口, 过滤亏损股)
├── 估值/财务因子改为周频计算
└── 实现决策融合层(先用简单加权, 回测标定权重)

Phase 4 (持续优化)
├── 分钟数据仅做盘中辅助信号
├── 季度财报期后全量回填财务因子
├── 数据库每月PRAGMA optimize
└── 探索DuckDB作为OLAP查询引擎(只读, SQLite保持为写源)
```

## 最终结论

| 评估维度 | 结论 |
|---------|------|
| **技术方案可行性** | ✅ **可行**, 三层结构在当前基础设施上可直接实现 |
| **性能风险** | 🟢 **低**, Mac Mini M4 + 16GB RAM足够承载全部新模块 |
| **数据管线完整性** | 🟡 **基本完整**, 6个短期因子中5个无需新数据源 |
| **最大风险** | 🔴 **因子算法实现链路不明确**, 需优先审查 |
| **成本** | 🟢 **零新增成本**, 全部利用已有Tushare接口和Hermes cron |
| **推荐开始方式** | 先优化SQLite配置 + 审查因子链路 → 再实现新因子 |

> **一句话总结**: 系统架构设计合理, SQLite性能远未到瓶颈, Mac Mini M4资源充裕。最大风险是因子管线核心算法的实现状态不明确, 需要优先确认。建议按"SQLite优化→审查现有因子→实现新因子→决策融合"的四阶段路线有序推进。
