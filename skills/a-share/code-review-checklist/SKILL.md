# 代码审查检查清单

## 用法
4-Agent 评审时，worker 必须先加载此 skill 获取对应场景的清单，
**逐项执行验证后再写评审报告**。

## 通用基线（所有评审必检）

| # | 检查项 | 验证方法 |
|:-:|:-------|:---------|
| 1 | 数据库列类型 vs Python 比较操作符兼容 | `PRAGMA table_info(xxx)` 确认类型，检查 `== '1'` / `== 1` / `is None` 混用 |
| 2 | 文件路径在运行时 CWD 下存在 | `ls <path>` 确认文件存在 |
| 3 | shell 脚本可执行 | `stat -f %A <file>` — 确认有执行位 |
| 4 | 数值单位转换链无重复 | 从源 API → DB → 引擎 → 输出，追踪 元/万元/亿元 |
| 5 | 日期格式跨表一致 | `SELECT typeof(trade_date), trade_date FROM xxx LIMIT 1` 对比 |
| 6 | SQL 参数化（无 f-string 拼接） | grep 搜索 `f"`+WHERE 中直接拼接变量 |
| 7 | 连接释放 | 每个 `conn` 必须有 `close` 或 `with`，try/finally 包裹 |
| 8 | 空结果集防御 | `fetchone()` 后 `is None`；`fetchall()` 后 `len()>0` |
| 9 | 异常无敏感信息泄漏 | except 中不 print 含 Token/密码/API Key 的变量 |
| 10 | API 重试机制 | Tushare 等外部调用需 sleep + 重试 |

## 五轴评审框架（通用工程向，移植自 agent-skills）

在完成上述量化场景检查后，按五个轴逐项过一遍改动。**批准标准**：该改动只要整体上改善代码健康就该批，不需要完美——完美代码不存在，目标是持续改进。不要因为"不是我会那么写"而拦一个改动。

### 1. Correctness 正确性
- 是否匹配 spec/任务要求？边界情况（null、空、边界值）？
- 错误路径是否处理（不只 happy path）？
- 测试是否真的在测对的东西？改动能被回归测试抓住吗？
- 有无 off-by-one、竞态、状态不一致？

### 2. Readability & Simplicity 可读性
- 命名是否描述性且符合项目约定？（无裸 `temp`/`data`/`result`）
- 控制流是否直白？（避免嵌套三元、深层回调）
- **能否更短？**（1000 行能 100 行完成就是失败）
- **抽象是否挣到它的复杂度？**（第三个用例出现前不要泛化）
- 有无死代码：no-op 变量、向后兼容 shim、`// removed` 注释？
- **新条件分支是否焊到无关流程上？** 设计异味——推进独立 helper/state/policy。
- **同类条件是否反复出现？** 说明缺模型或分发器。"临时"分支通常是永久债。

### 3. Architecture 架构
- 是否遵循现有模式？引入新模式的理由成立吗？
- 模块边界干净吗？有无该共享却重复的代码？
- 依赖方向正确吗（无循环依赖）？
- **这次重构是降低复杂度还是只是搬运？** 数读者需要把握的概念数。让整支分支/模式/层消失的重构 > 重新集中同一逻辑的重构。删抽象优于抛光抽象。
- **特性逻辑是否泄漏进共享/通用模块？** 逻辑留在属主层，复用现有 canonical helper 而不是近重复。
- 类型边界是否显式？质疑滥用的 `any`/强制转换/静默回退。

### 4. Security 安全
- 用户输入是否验证/清洗？密钥是否避开代码/日志/版本控制？
- SQL 是否参数化（无字符串拼接）？
- 外部数据流（API、日志、配置、DB 结果）是否在边界验证后才进逻辑？
- 依赖是否来自可信源、无已知漏洞？

### 5. Performance 性能
- 有无 N+1 查询、无界循环、无约束数据拉取？
- 热路径里有无大对象、同步操作该异步的？
- 列表接口缺分页？

### 结构性修复建议
标出结构问题时**提出移动方案**，不只说"这复杂"：
- 条件链 → 类型化模型或显式分发器；重复分支 → 折叠为单一清晰流
- 编排与业务逻辑分离；共享模块里的特性逻辑移到属主包
- 复用 canonical helper 替代定制近重复；显式类型边界让下游分支消失
- 删除无意义透传包装；抽取 helper 或拆分大文件
- **优先让部件消失的方案**，而不是把复杂度摊开

### 评审发现分级
| 前缀 | 含义 | 作者动作 |
|:---|:---|:---|
| 无前缀 | 必须改 | merge 前必须处理 |
| **Critical:** | 阻止合并 | 安全漏洞、数据丢失、功能破坏 |
| **Nit:** | 可选小项 | 可忽略（格式、风格偏好） |
| **Optional:/Consider:** | 建议 | 值得考虑但不强制 |
| **FYI** | 仅信息 | 无需动作，供未来参考 |

**按杠杆排序**：正确性/安全优先，然后结构性回归和漏掉的简化，最后其他。一个高置信度评论胜过一长串。一个结构问题和十个 nit——结构问题就是评审本身。

### 评审者防自欺表
| 借口 | 现实 |
|:---|:---|
| "我过了每行，没问题" | 过行 ≠ 验证。至少跑一次 SQL/脚本（见上方运行时校验），再下结论。 |
| "这个 bug 小，不说了" | 分类过的小 bug 也是发现。标 Nit 让作者知情，别吞。 |
| "改动太大没法细审" | 太大就要求拆分，不是降低标准。 |
| "跟现有代码风格一致就行" | 现有风格也可能是坏的。报 Readability/Architecture 轴，不默认现有即正确。 |
| "作者是大模型，应该是对的" | 模型同样会犯类型/单位/路径错误。按清单逐项验证。 |
| "用户说没问题了" | 用户的"是"若跟着含糊表述可能是空"是"。用 review-process-enhancement 的断言声明段确认。 |
